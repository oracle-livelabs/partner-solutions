# IncidentData LiveStack replication runbook

This branch packages a full-demo **test candidate**. An export audit, local tests and container probes do not establish that a fresh OCI deployment works. Steps 4–6 below are required before declaring the milestone reproducible.

## 1. Prepare the immutable release

Work on `deployment/oci-resource-manager`; keep the existing milestone/main and live containers available. Do not repoint FU40 helpers at a new database. Source export helpers explicitly guard FU40; destination installers accept only the newly generated `IDxxxxxx` database and refuse an unowned populated CRIME_DATA schema.

The private staging directory `artifacts/` must contain the encrypted schema dump/manifest, three APEX exports/manifest, native AI configuration, two approved voice model files, current synthetic scenario declarations and SQLcl. It must never be committed to Git. Do not copy the entire historical Detective Room directory, OCI API-key configuration, wallet, private conversations or source developer accounts. The dump password is a separate 0600 `.secret` file.

Run the source scripts only on the authorised source VM. `export_database.cjs --plan` is read-only. `--export`, `--status`, `--download` and `audit_database.cjs` create/read uniquely named export artifacts and metadata jobs; they do not change application rows. The encrypted export excludes private table data and scheduler helper tables. Keep the successfully audited export prefix tied to the manifest. Never mix dump parts or keys from superseded attempts.

Run application tests, production frontend build, bootstrap tests, Terraform validation, standalone image builds and offline worker probes. Record exact results in `inventory/local-validation.json`. Commit application and bootstrap code before running `python3 scripts/build_release.py`. This creates an immutable code archive from that Git commit, an explicit allowlist of release payloads with SHA256 and byte sizes, and `artifacts/incidentdata-resource-manager.zip`. The small Resource Manager ZIP contains no dump password, wallet, participant passwords or large data/model payloads.

For the next test, use the current `deployment/oci-resource-manager` branch and rebuild the release and Resource Manager ZIP together. The Detective Room structured-output fix starts at commit `31f463c`: extraction requests a bounded JSON schema with the supplied source IDs, and other authoring calls request JSON objects. Source citations, exact-name checks and the single corrective retry remain enforced. Earlier release payloads do not acquire this fix when GitHub changes. The standalone Terraform worker build copies the current `backend` directory, including `oci-auth-provider.js`; the incremental `fu_edge` image under `scripts/` is only for updating the existing development worker.

The bundled SQLcl archive is Oracle's version-pinned distribution. Retain its included licence notices and confirm distribution terms before sharing outside the approved internal deployment use. Voice-model licensing/provenance remains recorded in `detective-worker/models.manifest.json` and the original model distribution.

## 2. Review the proposed deployment before spending

Destination: tenancy **apacanzset03**, compartment **franco_ucci_sandbox**, **ap-sydney-1**. Confirm the actual OCIDs and a Sydney availability domain using the read-only inventory. Supply the operator's SSH public key. Leave the SSH CIDR blank to disable inbound SSH, or supply a trusted public IPv4 /32 (up to /24 supported). Do not use an unrestricted SSH CIDR.

Review the complete Terraform Plan, IAM statements, quota/capacity, private release publication and costs. Initial sizing: E4 Flex 4 OCPUs/32 GB, new ADB 2 ECPUs/100 GB, 100 GB boot disk. The preliminary worksheet is approximately USD 20.48/day / 623.02 per 730 hours before GenAI, extra backups, egress/requests, taxes and tenancy discounts. Final architecture includes a private artifact bucket, private status bucket, a temporary credential object, reserved public IP, VCN and narrowly scoped runtime identities; refresh the estimate for the actual Plan. Agree a spending limit and retention window before publication or Apply.

**Public APEX tradeoff:** this candidate uses Oracle's managed public HTTPS endpoint and a public SQL network endpoint with mandatory mTLS and database credentials. It is not a private ADB endpoint. The VM exposes HTTP/HTTPS and operator-limited SSH; port 3001 and Ollama bind to loopback. Individual React accounts use HTTPS Basic authentication, fixed server-side personas and same-origin writes. APEX imports select Oracle APEX Accounts. Review public APEX pages and account-to-scope behaviour during acceptance.

Keep AI region separate: source-parity models are configured in Chicago because the source model catalogue is not fully available in Sydney. This sends model inference requests/data to that service region. Check destination model availability, permissions and inference charges before Apply.

The initial destination preflight found the Vault quota exhausted. The approved short-lived demo design now uses a temporary private Object Storage credential object, so no Vault/key/secret or additional Vault quota is required. The few-hour test now authorises the exact VM/ADB principal IDs directly and creates no dynamic groups. A sandbox policy creation/deletion probe passed in the Sydney IAM home region. Read [STEP4-REVIEW.md](STEP4-REVIEW.md) and refresh these checks before publication or Apply.

## 3. Publish approved private release

Only after the reviewed deployment/cost approval, use `scripts/publish_release.py` with destination compartment OCID, a dedicated release bucket and immutable version prefix. The default mode prints a local publication plan and makes no cloud calls. `--publish` creates or verifies a private, versioned bucket in that compartment, checks local hashes and uploads only the manifest allowlist; it refuses conflicting content at an existing version prefix. No public bucket or write-capable PAR is required. The publication bucket is intentionally maintained separately from an individual demo stack so Destroy cannot erase the source release.

Keep `database/export-password.secret` separate. Supply it as the **sensitive** `dump_password` Resource Manager variable; never put it in Git, screenshots, shell history or non-sensitive tfvars. Resource Manager state contains generated credentials/wallet material: restrict state/stack access to authorised operators. VM metadata contains only the installer and non-secret configuration.

## 4. Create Resource Manager stack and Plan

Upload `incidentdata-resource-manager.zip`, selecting **`terraform` as the working directory** and **Terraform 1.5.x** (the verified CLI runtime is 1.5.7). The schema is bundled at `terraform/schema.yaml`. Select the confirmed tenancy/compartment/Sydney region and AD, SSH values and private release coordinates. Leave `public_hostname` blank for `https://<reserved-public-IP>`. Use the pinned Ollama image digest provided by the package. Do not change the bundled release manifest to bypass a failed gate.

Create and inspect a **Plan job first**. Verify every resource is new, scoped to the sandbox and tagged IncidentData; no existing database or VM should be updated/imported/destroyed. Check policy/resource creation permissions in the sandbox; no tenancy-level dynamic groups are required. Save the reviewed Plan and estimate. Apply only after the explicit approval described above.

## 5. Apply and monitor installation

Apply generates fresh ADMIN/schema/wallet/account passwords and a database wallet. Terraform uploads these, together with the separately supplied dump key, to one object in the new private bootstrap bucket. The upload uses a write-only, single-object PAR expiring after three hours; the new VM reads through its instance identity. Passwords and upload tokens are absent from VM metadata and Git. The VM verifies the payload checksum, deployment and release identity, and keeps a 0600 recovery cache for retries. VM/ADB principals read private artifacts and call GenAI; no source API keys are copied. Terraform writes a non-secret runtime object after reserving/attaching the public IP, avoiding a dependency cycle. The VM waits for IAM propagation, verifies every downloaded artifact and restores only the target DB. It rebuilds app/media images, imports APEX and native AI, provisions participant accounts, pulls the local Ollama model and starts services.

The VM startup script uses gzip before Base64 encoding to remain below OCI's 32,000-byte metadata limit; [cloud-init accepts gzip user data](https://cloudinit.readthedocs.io/topics/format.html). Plan review checks the rendered payload size and script header when known. A fresh Plan cannot resolve the ADB URL and credential checksum yet; a VM lifecycle precondition enforces the encoded JSON byte bound before launch, and the review records that deferred check explicitly. Temporary upload/status links retain their original expiration during retries.

In Resource Manager logs, watch `Bootstrap: running / <stage>`. The status callback is bound to deployment ID, instance OCID and release hash. Apply waits up to 120 minutes and fails on a failed callback, identity mismatch or timeout; successful VM creation alone is insufficient. Bootstrap completion means automated checks passed; human walkthrough acceptance is still pending.

On the **new target VM**, inspect `sudo cat /opt/incidentdata/state/bootstrap-status.json`, `sudo journalctl -u incidentdata-app -u incidentdata-worker -u incidentdata-gateway`, and root-only `/opt/incidentdata/logs/`. Never paste private configuration, env files, wallet files or bootstrap credential caches into shared logs. First-boot dependency failures can occur before callback delivery; inspect `/opt/incidentdata/logs/firstboot.log` and cloud-init logs if status remains pending.

On failure, preserve diagnostics and failed resources for investigation. Do not drop/reimport a partially populated schema blindly. Reapply is safe only for the same recorded completed schema/release; an incomplete import intentionally requires operator diagnosis or a fresh stack. To rerun a corrected same-release installer on the new VM, use its existing root-only config with `/opt/incidentdata/installer-venv/bin/python /opt/incidentdata/install.py /opt/incidentdata/state/bootstrap.json`; verify the stage/idempotency conditions first. Application/schema upgrades require a separate migration design rather than overwriting this baseline.

After automated acceptance and the public HTTPS health check pass, the VM deletes only its own bootstrap credential object using an ETag condition and verifies it is absent before reporting ready. The callback contains no passwords. Read/delete permissions cover that exact object; the ADB principal cannot read the bootstrap bucket. A failed install retains the private object and root-only cache for diagnosis/retry. An acceptance marker prevents a cleanup retry from repeating the mutating nine-city acceptance; the public health check still runs.

The one-time uploader is a `terraform_data` creation action rather than a managed credential-object resource, so a normal Terraform refresh/reapply does not recreate the deleted object. Do not force-replace the uploader to republish credentials without a deliberate recovery plan. The write-only upload token expires after three hours and cannot download the object. Root-only credential caches/runtime files and protected Resource Manager state remain sensitive until the demo is destroyed.

## 6. Public walkthrough acceptance

Retrieve the sensitive `participant_accounts` Terraform/Resource Manager output through the authorised operator interface. Sensitive outputs are masked in ordinary Terraform output; authorised explicit retrieval/state access exposes them. On the VM, the root-only bootstrap recovery cache also holds these generated accounts. Browser persona selection is disabled in public mode. Basic sign-out normally requires closing the browser profile; use separate browser profiles for role comparisons. Do not share the operator account as a general participant account. Existing synthetic seed batches may be operator-owned; ordinary analysts can create their own batches within their scope.

From outside the OCI subnet, open the React IP URL with normal TLS verification. Confirm unsigned access fails, accounts have the intended scope and a forged `X-Demo-User` cannot elevate permissions. Sign into each with its fresh participant account. On newly provisioned ADBs the developer portal `/ords/apex` uses database SSO; use the database administrator credentials there for administration rather than directing participants to that portal. Confirm no Open Door/public page exposes protected data, native AI flows work and each account maps to the intended scope. Record the actual application URLs after successful import. Automated bootstrap verifies the actual public username/password form for each app, the configured schemes and persisted participant accounts; it does not substitute for successful authenticated browser checks.

Generate a **new** Detective Room from source batch BLOBs and declared fictional associations. Keep ports 80/443 reachable for validation. Inspect gateway logs and the real certificate expiry/renewal from a trusted browser/openssl; six-day IP certificates require reliable automatic renewal. Observe an actual renewal before claiming renewal acceptance. Do not bypass certificate validation or leave staging certificates in a public walkthrough.

Finally reproduce from the packaged Git commit/release without reading the original VM. Mark the milestone deployable only after the fresh ADB, React/APEX endpoints, nine restores, AI/media generation and external walkthrough all pass.

## Retention and cleanup

Stop/start billable resources as supported when testing ends; storage/backups can continue to accrue costs. Review a **Destroy Plan** separately before deleting the target stack. Destroy removes the new VM/boot volume, ADB and stack networking/status objects/identities; it does not delete FU40/FU30, the original VM or the separately maintained private release bucket. No Vault/key/secret is created. Review remaining resources/backups and charges afterward. Delete the publication bucket and all versions only under a separate explicit retention decision. Never destroy resources by broad compartment-wide filters.

## Few-hour validation run

The owner approved **USD 20** for this first few-hour test, followed by deletion of its new resources. This is a planning budget, not an instant OCI billing cutoff. The local operator uses `scripts/test_stack.py` with a protected test-state JSON file to create an isolated Resource Manager stack, review its Plan, publish a dedicated private release bucket and Apply only that reviewed Plan. Every later operation checks the exact stack OCID, compartment, unique display name and run tag. A six-hour user-systemd timer runs the same guarded cleanup command as a fallback; normal teardown can run earlier after testing. The original VM/FU40/FU30 are outside the stack state.

Cleanup cancels any still-running test job, removes any failed bootstrap credential object in the recorded private bootstrap bucket, runs Resource Manager Destroy, deletes all versions in the dedicated test publication bucket, then removes the test control stack. It keeps the versioned Git code and protected local release payload for later sharing. Inspect the saved state/status and post-destroy OCI inventory; do not claim cleanup succeeded if a Destroy job or verification fails.

Direct principal policies use Oracle's documented `any-user` form, with an exact `request.principal.id` condition on **every** statement. This permits only the new VM or new ADB, with the same bucket/object and inference scopes as before; it does not grant access to arbitrary users. References: [principal-restricted IAM examples](https://docs.oracle.com/en-us/iaas/Content/data-integration/using/policy-examples.htm), [GenAI authenticated-principal policy semantics](https://docs.oracle.com/en-us/iaas/Content/generative-ai/add-api-permission.htm).

For a failed first Apply, keep the same frozen release manifest and stack. Update only the corrected Resource Manager ZIP, run `test_stack.py replan --state <private-state-file>`, then `review` before `apply`. Retry review permits existing unchanged resources plus additions; replacements, updates, deletes, original database/VM IDs and public SSH remain rejected. A failed application import needs stage-specific diagnosis, not a blind infrastructure retry.

The target expands its root filesystem with Oracle `oci-growfs -y` before payload installation. An authenticated Run Command operator may invoke `sudo /usr/local/sbin/incidentdata-bootstrap-status` to read fixed bootstrap diagnostics, or `sudo /usr/local/sbin/incidentdata-bootstrap-resume` to rerun only the original root-owned installer with its fixed private configuration. Both reject arguments. Resume clears the caller environment and takes the same exclusive installation lock as first boot; neither grants an arbitrary root command. Its IAM execution permission is restricted to that exact new VM and its own command executions.

VM recovery after an early first-boot failure is a separate review: verify and retire only the exact failed test instance, retain its ADB and reserved IP, then Plan again. The recovery reviewer additionally permits updating the test policy/IP assignment and replacing only the fixed non-secret runtime object and readiness provisioner. It still rejects database deletion/replacement and changes to the original VM/ADB IDs.

Source packaging omits the obsolete `adelaide_v2_tile_20260917` and `europe_profile_tiles_20260917` trees and rejects non-regular archive members. The installer also ignores those exact unused trees in older frozen releases, without following their dependency links; links and traversal elsewhere remain rejected. When recovering a retired VM, reset only its private callback object to the same deployment/release pending record after termination, before applying the reviewed replacement Plan.

Schema bootstrap restores the inventoried application roles, direct DDL/data-grant privileges and stable spatial/vector/RLS/cloud API grants before Data Pump import. `inventory/schema-runtime-privileges.json` records the source grants and managed-package normalization. The source Spatial Studio-only `SPATIAL_AUTHOR` membership is recorded separately; fresh ADMIN cannot grant it with ordinary SQL, and it is not needed for React/APEX spatial queries. See [Spatial Studio user setup](https://docs.oracle.com/en/cloud/paas/autonomous-database/serverless/adstu/set-spatial-studio-users-and-privileges.html) for optional authoring access.

The portable native-security restore excludes generated XS/RAS implementation metadata from Data Pump, then runs three checksum-verified source demo SQL scripts. It compares all 20 data grants and the cross-table parent requirement against the captured source baseline. It does not copy source end-user credentials. APEX imports run as the fresh database ADMIN with an explicit workspace context; the application schema does not receive APEX instance administration privileges. The deployment uses a workspace identifier representable exactly in JavaScript, commits all five new participant accounts, and replaces legacy fixed-identity login pages in apps 319/320 with the exported secure login form from app 361. Original application exports remain intact.

The first cloud test proved the clean schema restore, native-security parity, destination resource-principal inference and three APEX application imports with five persisted accounts. Its public APEX routes did not pass browser acceptance. These partial checks do not establish a deployable release; the corrected package requires a fresh full-stack test and teardown.

Public IP TLS behind OCI NAT also requires Caddy `default_sni <public-IP>` so ordinary clients that omit the TLS SNI extension receive the IP certificate. Without it, a certificate can be valid while standard Python/Node/browser connections fail. The isolated `scripts/test_gateway_tls.py` regression reproduces the failure and checks the correction on loopback, using a temporary trusted test certificate without public issuance. Production acceptance continues to use the standard public trust store. See [Caddy default_sni](https://caddyserver.com/docs/caddyfile/options#default_sni). A corrected-bootstrap VM recovery may update the release gate and one-time uploader only while every data/model/APEX/AI artifact and the deployment identifier remain unchanged.
