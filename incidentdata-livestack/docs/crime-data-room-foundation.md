# Data Room — foundation release

Historical first-increment notes. See [the current seven-stage workspace guide](crime-data-room-workspace.md) for deployed features. The original storage and ingestion safeguards below still apply.

## Available now

The existing IncidentData app has a **Data Room** navigation entry with all six planned sections. This first increment implements ZIP upload, a preallocated Batch ID, real browser upload progress, durable storage, file inventory, deterministic inventory headlines, scoped batch history, and three processing stages. All batch data is stored in the existing OCI-hosted ADB schema, not browser/local ephemeral storage.

Original ZIPs and extracted files are retained as BLOBs, with SHA-256 checksums. This is a bounded demo foundation; Object Storage pointers can replace the BLOB storage adapter in a later increment if needed. No existing incident, POI, graph or city-profile rows are modified.

## Demo sequence

1. Refresh the app and select **Data Room**. Use the statewide administrator or an analyst demo user.
2. Select **Download sample ZIP**. It has eight synthetic files: one TXT narrative, three CSVs (bank transactions, travel, messages), two JSON documents, and two existing staged PNG scene photos.
3. Choose the downloaded ZIP, confirm it contains synthetic training data, and select **Load ZIP**.
4. Observe the allocated Batch ID and upload percentage. At 100%, the browser has sent the bytes; ADB storage confirmation and processing follow separately.
5. Review **Content Stats**, filter **Content Headlines**, and use **Details** or **Download** to inspect an original item. CSV counts assume the first record is the header. Text previews contain at most 6,000 characters.
6. Inspect the pipeline: **Load → Unzip → Ingest** complete. The batch becomes **Inventory ready**, not AI-investigation complete.
7. Revisit the batch from **Batch Load History**. Upload and created timestamps are distinct and displayed in the browser's local time.
8. Switch to another analyst demo user to demonstrate isolation. The statewide administrator can see all batches; analysts see their own; the read-only demo user cannot upload/retry/cancel.

The supplied photos are reused staged demo assets. Their filenames inside the ZIP do not encode POI names. No face identification, person-photo association, similarity score or graph link is generated by this release. No separate answer key is ingested into the pipeline.

## Explicitly not enabled yet

- LLM-based Identify/Describe (current headlines are labelled **Inventory-derived · not AI-generated**).
- Learn-what-is-there, Understand-Connections, Create-Data-products.
- Embeddings, relationship graph, native ADB agent-tool orchestration for these batches.
- Select AI batch chat and saved conversations. Section F is an explicit placeholder, not a working chat control.
- OCR or image decoding/visual analysis. The loader checks PNG/JPEG signatures, not complete image validity.

The existing app's other Select AI/agent capabilities remain unchanged. Do not run the existing agent setup script to enable this foundation: it is not required. Future agent tools should retrieve scoped content, treat uploaded text as untrusted data (never instructions), persist provenance/model versions, and distinguish proposed relationships from reviewed links. General image similarity must not be presented as confirmed identity.

## Data model and queue

- `CDR_BATCHES`: original archive BLOB/hash, uploader, timestamps, status, counts, one-line summary, errors, worker lease and attempt count.
- `CDR_ITEMS`: source path, stable item ID, original content BLOB/hash, type, inventory headline, bounded text preview and CSV row count.
- `CDR_STAGES`: seven per-batch stage records, statuses and timing.
- `SECURE_CDR_BATCHES_V`, `SECURE_CDR_ITEMS_V`, `SECURE_CDR_STAGES_V`: uploader/admin visibility via `SYS_CONTEXT('USERENV','CLIENT_IDENTIFIER')`.

These tables are independent of the replaceable city-profile seed data. The demo user is derived from the existing server context, never an upload-supplied `loaded_by` field. This app uses a demo-user header, **not production authentication**. Real data requires authenticated identity, production authorisation, retention/deletion policy, malware scanning, audit hardening and operational review before use.

An ADB queue is polled by the existing Node app every 2.5 seconds. Only one batch is processed per app instance at a time. Claims use a token and 90-second lease; every persisted processing step rechecks ownership while locking the batch. After an app restart, an interrupted batch is reclaimed when its lease expires. Retry reuses the original ZIP and stable item IDs, rebuilding only that batch's derived inventory. A duplicate submission of identical archive bytes is idempotent. A different ZIP requires a new Batch ID.

Failed ZIPs remain visible with an error; only stored failed archives can be retried. Unfinished uploads can be cancelled without deleting their history. Cancelled uploads have no stored ZIP and cannot be processed. A demo user is limited to ten unfinished upload/processing records. History currently returns the latest 100 visible batches; older records remain in ADB but pagination is a later enhancement.

## Ingestion limits

- ZIP: 20 MiB maximum; 100 content files; 500 total archive entries.
- Expanded content: 40 MiB total; 8 MiB per file.
- Formats: TXT, CSV, JSON, PNG, JPG/JPEG, MP3, M4A and MP4. Text must be UTF-8; CSV is bounded at 20,000 data rows and 200 columns.
- Unzip validation deadline: 30 seconds. Actual streamed bytes, reported sizes and CRC checks are validated.
- Reject unsafe paths, duplicate paths (including case-only differences), symlinks, encrypted entries, unsupported compression, nested ZIPs and unsupported file types.
- Ignore only `.DS_Store` and `__MACOSX/` metadata entries; report the ignored count.
- Archive paths are never extracted to the server filesystem. File downloads are attachments with `application/octet-stream`; previews render as escaped text, not HTML.

## Setup and verification

Apply the additive, repeatable migration using the existing app's Oracle environment:

```sh
node scripts/setup_data_room.js
```

The server expects the migration to have been applied before enabling the worker. Schema provisioning is explicit, not performed per HTTP request. `Containerfile` includes the migration script and installs the committed root lockfile. The running demo was updated in place; rebuild the container image from this workspace for future recreation.

```sh
node test/data-room-archive.test.js
node test/incident-semantic-search.test.js
node test/result-relationships.test.js
npm run build
```

Optional live API verification writes three clearly named synthetic fixtures (valid, intentionally invalid, cancelled). It is not run by the default unit-test command:

```sh
node scripts/test_data_room_live.js --run-synthetic-tests
```

The live test checks stored bytes/checksums, five demo-user scopes, ignored spoofed uploader input, idempotent upload, visible failures, retry and cancellation. These verification batches remain in history deliberately; they are not real incidents.

Initial live verification on 12 September 2026 passed 18 unit cases, the API checks above, a Chromium upload of all eight sample items, format filtering, source previews and demo-user switching. A simulated interrupted verification batch was reclaimed after an app restart, reused its stable item IDs, and returned to inventory-ready on attempt two; the separate eight-item sample batch also remained intact.

Sample batch available for revisiting: `DR-20260912-38be78f8-7a8c-448a` (statewide administrator).

Initial deployment backup of the previous backend entrypoint, UI index and package manifest: `/tmp/crimedata-room-backup.XHMpIS`. Older hashed frontend assets were retained in the running container. No existing incident or profile data was removed.

MP3/M4A/MP4 originals are retained with checksums and downloads. Stage 4 Identify/Describe transcribes MP3/M4A audio, saves an unreviewed machine transcript and describes it for later analysis. MP4 video analysis remains unavailable; supply JPG/PNG stills or TXT transcripts for video analysis. Existing upload and expansion limits apply.
